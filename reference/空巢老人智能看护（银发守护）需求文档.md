## 1 引言

### 1.1 项目背景

我国居家空巢、独居老人数量庞大，老人居家生活面临多重现实难题：容易忘记服药作息、跌倒等意外发生后求助渠道不畅、日常缺少情感交流慰藉；同时市面上多数养老产品仅做到被动提醒、单点监控，老人操作智能设备门槛高；缺少从异常事件感知、识别到家属、社区联动处置的完整业务闭环。

本项目银发守护是空巢老人智能看护 Agent 系统，定位为面向空巢、独居老人的智能看护辅助工具，不替代医疗诊断，不提供医疗救治。系统实现安全监护、用药作息提醒、情感陪伴、家属远程协同。老人端以安卓 / 鸿蒙手机、智能音箱作为主要使用入口，原型可采用 Python + 语音 SDK 模拟实现；家属端为微信小程序；搭建 Agent 中枢云端服务；可扩展接入摄像头、毫米波雷达、老人穿戴设备，该部分属于扩展预留能力。整体构建感知-理解-规划-执行-反馈-记忆完整服务闭环。

### 1.2 文档目的

本文档定义空巢老人智能看护系统的功能需求、质量需求、约束限制条件，为后续系统架构设计、原型开发、测试提供依据，文档依据课程实验要求和小组内部约定，统一 P0/P1/P2 优先级口径。

### 1.3 预期用户

核心用户为空巢、独居老人，是系统主要服务对象，交互以语音为主，操作简单，适配老年人的使用习惯。次要用户为家属，可以远程查看老人状态，配置提醒规则并且接收风险告警。潜在用户是社区养老工作人员，能够接收系统推送的高危告警信息，及时开展线下帮扶工作。

## 2 功能需求

系统整体分为老人端 AI Agent、家属微信小程序端、Agent 中枢服务三大部分，业务包含日常主动陪伴、居家安全监护、家属远程联动、多模态指令交互四大模块，并设置公共辅助功能。功能需求编号与优先级如下。

## 3 质量需求（非功能需求）

依据课程实验要求和小组内部约定，本项目质量属性整体优先级为：

- 高优先级质量属性：可用性、安全性、可靠性。
- 中优先级质量属性：可修改性、性能、易用性。

质量场景采用六要素描述：刺激源、刺激、环境、制品、响应、响应度量。每个场景标注场景编号、优先级、相关功能需求和架构策略，作为后续架构设计与架构评审的依据。

### 3.1 质量场景六要素说明

| 要素 | 含义 |
| --- | --- |
| 刺激源 | 发起刺激的人、系统或外部事件 |
| 刺激 | 到达系统的具体事件或请求 |
| 环境 | 系统当前所处的运行状态 |
| 制品 | 系统中对刺激做出反应的部分 |
| 响应 | 系统接收到刺激后的行为 |
| 响应度量 | 对响应结果的可量化衡量 |

优先级映射：H 对应 P0 核心业务，M 对应 P1 重要业务，L 对应 P2 扩展业务。若场景重要程度高但原型实现优先级为 P1，则在表中分别标注，例如“H/P1”。

## 4 限制条件（约束需求）

限制条件是系统在需求、设计、实现和运行过程中必须遵守的边界条件。依据课程实验要求和小组内部约定，本项目限制条件分为五类：

| 类别 | 编号前缀 | 含义 |
| --- | --- | --- |
| 业务约束 | CON-B | 由项目定位、业务范围、用户场景决定的约束 |
| 技术约束 | CON-T | 由技术选型、硬件能力、接口方式决定的约束 |
| 开发与成本约束 | CON-D | 由课程实验周期、人力、成本、原型目标决定的约束 |
| 法律伦理约束 | CON-L | 由个人信息保护、隐私伦理、医疗边界决定的约束 |
| 运行与环境约束 | CON-E | 由部署环境、网络条件、外部依赖决定的约束 |

### 4.6 限制条件与优先级关系

- **硬约束优先于软约束**：业务约束、法律伦理约束、部分技术约束属于硬约束，优先级高于功能扩展和性能优化。
- **P0 功能必须满足硬约束**：例如隐私授权、未授权不采集、告警只通知不急救等，必须在 P0 原型中落实。
- **P1 功能可降级或模拟**：如视觉跌倒识别、告警重试、离线降级等，允许原型阶段部分模拟。
- **P2 功能仅预留接口**：如毫米波雷达、穿戴设备、社区后台、高级情绪识别，不纳入原型完整实现范围。
- **限制条件与质量场景对应**：业务约束主要对应安全性、可靠性；技术约束主要对应可修改性、性能；开发与成本约束影响优先级划分；法律伦理约束对应安全性；运行与环境约束对应可用性、可靠性。

## 5 需求优先级划分

依据项目统一标准，P0 代表原型必须实现，答辩可演示；P1 代表尽量实现，可模拟替代；P2 代表仅预留接口，不需要完整编码。

**P0 级别的需求**包含用药作息提醒，支持语音或界面创建；老人主动语音求助；家属高危告警推送；家属小程序日志查看；家属配置提醒任务；基础语音交互，ASR、TTS 与基础意图理解；隐私授权开关；用户基础记忆档案；久坐计时提醒，依靠计时规则实现，不强制视觉。以上需求构成系统核心业务闭环。

**P1 级别的需求**包含视觉自动跌倒识别，依赖摄像头；主动情感陪伴闲聊；告警消息重试；网络断开离线降级；误告警手动取消；跌倒后语音通话；日志定期清理。该部分允许部分功能使用模拟逻辑。

**P2 级别的需求**包含毫米波雷达、穿戴设备接入；社区养老后台对接；高级情绪识别；社区批量部署优化，全部只预留抽象接口，原型阶段不进行完整编码。

## 6 假设与依赖

### 6.1 假设与依赖的说明

- **假设（Assumption）**：项目组认为在原型开发、演示和运行时会成立的前提条件。若假设不成立，需要调整需求或架构方案。
- **依赖（Dependency）**：系统必须依赖的外部条件、服务、硬件或人员配合。若依赖失效，系统应有降级或兜底方案。
- **与限制条件的区别**：限制条件是“必须遵守的边界”，假设与依赖是“希望成立或必须获得支持的前提”。
- **编号规则**：
  - AS：Assumption，假设。
  - DP：Dependency，依赖。
