# 通知状态查询、人工恢复与健康监测

以下命令只供具有应用数据库访问权限的受信任本地管理员使用。操作者参数是
审计署名，不是身份认证凭据；真正的访问边界是主机账号、文件 ACL 和运维权限。
不向普通客户端开放这些命令，不将凭证放入命令参数、原因或审计署名。

## 前置条件

- 从 `cloud-server` 执行，使用现有应用配置；`DATABASE_URL` 必须与命令中的
  绝对 SQLite 文件完全一致。命令核验原 engine、Session 工厂、实际 Session、
  文件及父目录身份，拒绝未知目标，不创建新的 engine。
- 先由管理员显式执行 `python -B -m scripts.migrate_edge_alert_receipts --database
  ABSOLUTE_SQLITE_FILE`。新增修订号及恢复审计表，保留历史告警和通知证据。
  应用启动不会建表；本轮没有在任何业务数据库执行迁移。
- 生产父目录应由受信任账号控制。路径身份检查不能彻底防御同账户并发替换。

## 只读查询

命令前缀均为 `python -B -m scripts.manage_notifications --database ABSOLUTE_SQLITE_FILE`：

| 子命令 | 用途 |
| --- | --- |
| `list-unknown --after-id 0 --limit 100` | 按通知 ID 分页查询未知记录；继续用最后一条 ID 作为 after-id，直至空页；单页上限 1000 |
| `show --receipt-id ID` | 查看指定记录及已提交恢复审计 |
| `status` | 聚合各状态数量、最老待处理记录等待时间及过期 sending 数量 |

查询不修改状态或发送通知。输出不包含告警正文、设备 JWT、认证头或认领标识。
最老等待时间从原接收时间起算，不表示最近一次重试已等待多久。
CLI 是另一个进程，不能读服务进程内存，返回 `worker.state=unavailable`；
这不表示工作者已经停止。服务就绪状态通过现有 `/health` 检查。

## 两种人工决策

在上述前缀后执行：

```text
keep --receipt-id ID --device-id DEVICE --elder-id ELDER --expected-revision REV --operation-id UUID --operator ADMIN --reason awaiting_evidence
retry --receipt-id ID --device-id DEVICE --elder-id ELDER --expected-revision REV --operation-id UUID --operator ADMIN --reason duplicate_risk_accepted --authorize-duplicate
```

每次新决策使用新的规范小写 UUID。`REV` 来自查询；`ADMIN` 为不含空白、
最长 64 字符的本地管理员署名。原因码仅允许 `reviewed_unknown`、
`awaiting_evidence`、`duplicate_risk_accepted`，不接受可能夹带凭证的自由文本。

两种操作均核验通知、设备、老人、当前家属绑定、启用状态、修订号与租约，
并拒绝已取消告警。条件更新和审计同事务提交；修订号递增，累计尝试不重置。
`keep` 不改变发送证据和 unknown 状态。`retry` 仅转为 `retry_wait` 并授予额外
一次认领额度，由原工作者处理；管理命令不直接发送。

**unknown 表示此前发送可能已成功，人工重试可能造成重复通知。** 初始自动
额度为 3 次，每份唯一人工授权增加 1 次；累计次数始终保留。授权不保证送达。
仍有效的 sending 不可人工恢复；过期 sending 由工作者保守转为 unknown，
不能据此推断此前未发送。unknown 从不自动重发。

同一 UUID 和相同参数可重复核对，返回原审计，不再增加额度；不同参数复用
UUID 会被拒绝。返回原审计仅证明该决策曾提交，不证明当前通知仍处于当时状态。
如果提交或资源关闭结果不确定，命令返回非零且不输出成功。先查询 `show`，
再用原 UUID 和原参数核对；不要盲目换 UUID 反复授权。失败不执行删表或清理。

## 工作者生命周期与恢复

当前进程可通过 `app.state.delivery_worker.health()` 查看状态、最后完成循环、
最后完成结果持久化的处理时间、受控错误及任务是否已结束/被观察。
`last_processed_at` 不表示终端送达。心跳只随真实循环完成更新，不另建定时
监控任务。任务完成回调主动取回异常并更新 failed，不必等到应用关闭。

公网 `/health` 正常仍为 200/healthy；工作者不可用、失败或心跳超过 10 秒等情况
返回 503/degraded，不返回内部诊断。running 加旧心跳不能证明循环未阻塞；
心跳也不证明数据库没有竞争或外部终端收到通知。

先排除错误原因，再由持有应用对象的受信任进程内控制代码显式调用
`await app.state.delivery_worker.restart()`，或正常重启服务。没有新增远程重启
API 或自动重启循环。旧任务未结束时拒绝替换；关闭超时保留任务句柄并报告
failed，不能宣称不配合取消的依赖已停止。有效租约仍由原任务持有；过期租约
恢复为 unknown。关闭与重启均不重置计数、不删除任务，也不自动清除 unknown。

本阶段未验证多主机部署或真实终端送达。WS 副作用无法和数据库原子提交或
回滚，不保证严格一次送达；发送函数返回不等于家属接收或确认。本阶段不提供
家属确认。生产 Reporter 与本地运维的当前实现见下述本地队列文档。

## 与本地 Outbox 运维的边界

以上云端命令恢复的是通知任务 unknown，不用于解除老人端发送阻塞。老人端
现有独立的 `python -B -m src.integration.outbox_admin` 入口，见
[本地告警队列](本地告警队列.md)。该入口必须停止 Agent 后取得同一队列锁，
只能操作显式绝对路径及匹配的设备、老人、云端绑定。

本地先用设备 JWT 查询 `/edge/alerts/receipts/{event_id}`：匹配接收回执及哈希
后只更新本地 received；查询失败不改状态；not_found 也不自动发送。显式授权
重排只影响本地 pending 和额外一次发送额度，不会触发通知 unknown 的重发。
云端 notified/attempt_returned、设备接收回执和家属确认始终是不同事实。

本地清理只针对终态证据满 30 天的 received/resolved，保留有界审计，不删除
未解决失败或修改云端历史。审计满后拒绝破坏性操作，不自动丢弃旧证据。
本地操作没有绕过设备吊销或老人归属校验的查询后门。
